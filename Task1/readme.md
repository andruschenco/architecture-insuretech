### 1. Стратегия масштабирования и отказоустойчивости

| Аспект                               | Решение                                                                                                                                                                                    | Где отражено на схеме                                        |
|--------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------|
| **Вертикальное масштабирование**     | Используется для **баз данных** (увеличение CPU/RAM на ВМ с PostgreSQL). Для приложений — неэффективно, т.к. требует перезапуска.                                                          | Не отражено явно (подразумевается для ВМ с БД).              |
| **Горизонтальное масштабирование**   | **Основная стратегия** для микросервисов. Количество Pod'ов (`core-app`, `client-info`, `aggregator`) увеличивается при росте нагрузки через HPA (Horizontal Pod Autoscaler) в Kubernetes. | Отражено блоками "Масштабируемые Pods" и комментарием о HPA. |
| **Дополнительные зоны безопасности** | **Используются 2 зоны доступности** (Москва и Санкт-Петербург). Это обеспечивает отказоустойчивость на уровне ЦОД и низкую задержку для пользователей из разных регионов.                  | Отражено двумя зонами                                        |
| **Почему выбраны 2 зоны?**           | RTO 45 мин и RPO 15 мин не достижимы в одной зоне. При падении одной зоны вторая продолжает работу. 2 зоны — минимальный набор для 99.9% доступности.                                      | Комментарий на схеме.                                        |

### 2a. Конфигурация развертывания в Kubernetes

| Аспект                                   | Решение                                                                                                                                                                                                                                                                                                                | Где отражено на схеме                                                                             |
|------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| **Тип кластеров**                        | **Независимые кластеры Kubernetes** в каждой зоне доступности.                                                                                                                                                                                                                                                         | Два отдельных блока `Kubernetes Cluster (Москва)` и `Kubernetes Cluster (Санкт-Петербург)`.       |
| **Почему независимые, а не растянутый?** | 1. **Изоляция сбоев** — проблема в одном кластере не затронет другой.<br>2. **Упрощение управления** — обновления, откаты и конфигурации не зависят друг от друга.<br>3. **Сетевые политики** проще настраивать внутри одного кластера.<br>4. **Локальная производительность** — каждый кластер работает с "своей" БД. | Комментарий на схеме: *"Выбраны независимые кластеры для изоляции сбоев и упрощения управления"*. |
| **Оркестрация**                          | В каждом кластере свои Master-ноды (control plane) и Worker-ноды. Автоскейлинг через HPA.                                                                                                                                                                                                                              | Подразумевается (не отражено детально, чтобы не перегружать схему).                               |

### 2b. Балансировка нагрузки

| Аспект                           | Решение                                                                                                                                                                  | Где отражено на схеме                                                        |
|----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| **Глобальный балансировщик**     | **DNS / Anycast** — направляет пользователя в ближайшую (или наименее загруженную) зону доступности.                                                                     | Блок `Global Load Balancer (DNS / Anycast)`.                                 |
| **Локальный балансировщик**      | **Ingress Controller (Nginx)** внутри каждого кластера. Распределяет трафик между Pod'ами внутри кластера.                                                               | Блоки `Ingress / Load Balancer (Nginx)` в каждом кластере.                   |
| **Health Checks (глобальный)**   | Глобальный LB проверяет **доступность всего кластера** (например, через эндпоинт `/health` на Ingress). При недоступности одного кластера — весь трафик уходит в другой. | Стрелки от Global LB к Ingress с пометкой `health check`.                    |
| **Health Checks (локальный)**    | Ingress проверяет **readiness** и **liveness** каждого Pod'а. Неготовые Pod'ы исключаются из балансировки.                                                               | Стрелки от Ingress к Pod'ам с пометкой `Health Checks: Liveness, Readiness`. |
| **Географическая маршрутизация** | Пользователь из Москвы → Global LB → Кластер в Москве. Пользователь из СПб → Global LB → Кластер в СПб.                                                                  | Отражено двумя зонами и стрелками от Global LB к обоим Ingress.              |

### 2c. Фейловер-стратегия

| Аспект                  | Решение                                                                                                                                                      | Где отражено на схеме                                                  |
|-------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------|
| **Стратегия**           | **Active-Active**. Оба кластера работают одновременно и принимают трафик.                                                                                    | Две активные зоны, обе принимают запросы.                              |
| **При сбое одной зоны** | Глобальный LB направляет **100% трафика** в живую зону. Время переключения — несколько минут (DNS TTL + health check timeout). Соответствует RTO = 45 минут. | Стрелки от Global LB к кластерам. При сбое одна стрелка "отключается". |
| **RPO**                 | Данные синхронизируются между зонами через **Master-Master репликацию** (асинхронную). Потеря данных при сбое одной зоны минимальна (секунды).               | Стрелка `Master-Master репликация` между БД.                           |
| **Восстановление**      | Автоматическое (через DNS и health checks). Оператор не требуется.                                                                                           | Подразумевается.                                                       |

### 2d. Конфигурация базы данных

| Аспект                       | Решение                                                                                                                                                                                                                      | Где отражено на схеме                                             |
|------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------|
| **Репликация внутри зоны**   | **Master → Replica (асинхронная)**. Replica используется для чтения (read-heavy нагрузка), Master — для записи.                                                                                                              | Стрелка `Асинхронная репликация` внутри каждой зоны.              |
| **Репликация между зонами**  | **Master-Master (асинхронная)**. Позволяет писать в локальный Master в каждом регионе. Конфликты разрешаются стратегией **Last Write Wins (LWW)**.                                                                           | Стрелка `Асинхронная репликация Master-Master` между зонами.      |
| **Резервное копирование**    | **WAL-G** или **PgBackRest** с потоковой передачей WAL в **S3-совместимое хранилище** (например, Yandex Object Storage). Полные бэкапы — ежедневно, WAL — каждые 5 минут. RPO = 15 минут достигается частотой WAL-архивации. | Блок `Backup Storage (S3)` + стрелки `WAL Streaming` от мастеров. |
| **Шардирование**             | **Не применяется** на данном этапе. Объем данных — 50 ГБ, что легко обслуживается одним Master'ом. В будущем, при росте > 1 ТБ, можно рассмотреть шардирование по `client_id`.                                               | Комментарий на схеме (добавлю позже).                             |
| **Инструмент управления БД** | **Patroni** + **etcd** для автоматического failover внутри зоны. Не отражено на схеме детально, чтобы не перегружать.                                                                                                        | Подразумевается.                                                  |
